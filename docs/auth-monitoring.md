# Авторизация и мониторинг

Этот раздел нужен для публикации сервиса через SWAG/nginx, Authelia/Authentik, CrowdSec и Prometheus. Базовая рекомендация: не открывайте `inpx-shelf` напрямую в интернет, а держите его за reverse proxy с HTTPS и внешней авторизацией.

## Авторизация за reverse proxy

Если сервис публикуется через SWAG, Authelia/Authentik и CrowdSec, не открывайте порт `12380` напрямую в интернет. Лучше держать `inpx-shelf` во внутренней Docker-сети или публиковать порт только на localhost:

```sh
-p 127.0.0.1:12380:12380
```

Для дополнительной защиты от обхода proxy можно включить обязательную внешнюю авторизацию:

```sh
-e INPX_REQUIRE_AUTH=true \
-e INPX_AUTH_MODE=proxy \
-e INPX_TRUST_PROXY=true \
-e INPX_PROXY_AUTH_HEADER=Remote-User \
-e INPX_TRUSTED_PROXY_CIDRS=172.18.0.0/16
```

В этом режиме приложение отдаёт UI, API, OPDS, книги и обложки только если запрос пришёл от доверенного proxy и proxy передал заголовок авторизованного пользователя. Прямой заход из LAN на случайно открытый порт получит `403 Direct access is forbidden`. `/health`, `/ready` и `/api/index-status` по умолчанию остаются открытыми для Docker/Unraid health-check; если нужно закрыть и их, задайте `INPX_AUTH_EXEMPT_HEALTH=false`.

Заголовок пользователя проверяется при каждом запросе, в том числе к API; cookie приложения его не заменяет. Настройте передачу `Remote-User` для всех путей приложения: UI, `/api/`, книг, обложек и OPDS.

Чтобы автоматически выбрать профиль, чей `login` совпадает с именем пользователя из proxy, добавьте `INPX_PROXY_BIND_PROFILE=true` (в `config.json`: `"proxyBindProfile": true`). Профиль выбирается без второго ввода пароля; переключение на чужой профиль запрещено сервером, включая личные списки OPDS. Для смены пользователя выйдите из SSO. Если совпадения нет, нужен обычный вход в профиль по логину и паролю. При включении этой опции заголовок доверенного proxy обязателен даже без `INPX_REQUIRE_AUTH=true`. По умолчанию привязка выключена.

## Сессия после входа

Ответ на вход в профиль сразу выдаёт новую cookie сессии: cookie, выданная до входа, вход не получает. Вход переживает перезапуск сервера: в `state.sqlite` хранится хеш id сессии и профиль, сами токены на диск не пишутся. Смена пароля и удаление профиля завершают его сессии; полное восстановление бэкапа и сброс пароля администратора (`--reset-admin-password`) завершают все.

Внешняя читалка из `bookReadLink` скачивает книгу без cookie браузера, поэтому книгу она не получит.

## Обязательный вход в профиль

По умолчанию анонимного доступа нет (гостевой доступ включается отдельно, см. ниже). До входа доступны только оболочка интерфейса и форма логина; поиск, личные данные, книги, обложки и OPDS требуют авторизации. Подготовьте профиль с логином и паролем либо настройте SSO-привязку выше. Администратор может войти с настроенными `adminLogin` / `adminPassword`. Профиль без пароля можно открыть только через SSO-привязку.

OPDS-клиенты и скачивание книг поддерживают Basic-авторизацию: общий логин/пароль из `opds.user` / `opds.password` или логин профиля с паролем OPDS. Пароль OPDS отдельный от пароля профиля: его создают в `Профиль и устройства → Устройства` (сгенерированный показывается один раз, свой - не короче 10 символов), новый заменяет старый. Пароль профиля в OPDS не подходит. Для авторизованного профиля доступны только его подборки. Без настроенной авторизации OPDS закрыт. У Kobo (токен устройства), KOReader (пароль KOReader) и API удалённой библиотеки `/remote/` (токен сервера, см. [config.md](config.md#remotelib)) своя авторизация; proxy-заголовок для них не нужен. Без входа открыты только health-проверки.

При запуске сервер пишет в журнал все свои HTTP-пути и для каждого - кто может его открыть (`Exposed HTTP paths`).

## Гостевой доступ

По умолчанию выключен. Включается переключателем `Гостевой доступ` в `Администрирование → Пользователи` или переменной `INPX_GUEST_ACCESS=true` (в `config.json`: `"guestAccess": true`). Гость без входа ищет по каталогу, открывает страницы авторов, серий и книг, скачивает и читает книги в браузере и видит общие полки витрины. Личных данных у гостя нет: списков, прогресса чтения, персональных полок, отправки книг и администрирования; попытка сохранить что-то открывает форму входа. Гость не может выбрать профиль, даже профиль без пароля, и не видит список профилей.

OPDS включается отдельно: флажок `Каталог без входа` в настройках общего OPDS (`Администрирование → Интеграции`) или `INPX_OPDS_GUEST_ACCESS=true` (`"opds": {"guestAccess": true}`). Без учётных данных открыты каталог и скачивание книг; профили, их подборки и прогресс (`/reading-profiles`, `/reading-lists`, `/reading-progress`, `?user=`) по-прежнему отвечают Basic Auth challenge, и читалка может войти с паролем OPDS. Неверные учётные данные гостевого доступа не дают: ответ 401.

Скачивание книг и обложки открыты гостю, если включён любой из двух переключателей. Если переменная окружения задана, она применяется при каждом запуске, и переключатель в администрировании недоступен.

Пароль профиля - не короче 10 символов. Кроме лимита по IP, вход в один логин замедляется после 5 неудач с любых адресов: каждая следующая попытка ждёт вдвое дольше, до 5 минут.

Внутренний rate limiting входа включён по умолчанию и полезен для локального режима или случайно открытого порта. Если весь внешний вход уже закрыт Authelia/Authentik, его можно отключить:

```sh
-e INPX_LOGIN_RATE_LIMIT_ENABLED=false
```

Счётчики попыток входа в `/metrics` при этом остаются, но само приложение не блокирует запросы по IP.

## Health-проверки

Для Docker, Unraid и мониторинга доступны лёгкие endpoint-ы:

* `/health` — жив ли процесс и готов ли HTTP-сервер
* `/ready` — готов ли сервер и построен ли поисковый индекс
* `/api/index-status` — ход индексации; источники, статистика и сведения о коллекции — только администратору (вход в веб-интерфейсе) и с токеном метрик (`Authorization: Bearer <INPX_METRICS_TOKEN>`)

Эти endpoint-ы отдают `Cache-Control: no-store`. В proxy-auth режиме они открыты по умолчанию, чтобы health-check контейнера не зависел от Authelia; закрыть их можно через `INPX_AUTH_EXEMPT_HEALTH=false`.

## Метрики Prometheus

Экспорт Prometheus по умолчанию выключен. Включить его можно так:

```sh
-e INPX_METRICS_ENABLED=true \
-e INPX_METRICS_TOKEN=strong-random-token
```

После этого метрики доступны на `/metrics` в формате Prometheus text exposition. Без `INPX_METRICS_TOKEN` `/metrics` закрыт. Prometheus должен передавать токен в заголовке `Authorization: Bearer strong-random-token`; query-параметр `?token=` не принимается. Путь можно изменить через `INPX_METRICS_PATH=/internal/metrics`.

Если включён `INPX_REQUIRE_AUTH=true`, `/metrics` подчиняется общей proxy-auth защите. Валидный `INPX_METRICS_TOKEN` разрешает scrape без `Remote-User`, что удобно для отдельного контейнера Prometheus.

В метриках есть технические счётчики индекса, БД, кэшей, источников, журнала событий, активных клиентов (`inpx_web_active_clients`, из них анонимных - `inpx_web_anonymous_clients`), авторизованных профилей онлайн (`inpx_web_users_online`; клиент и профиль считаются активными, если делали запрос за последние 5 минут) и попыток входа по результатам `success`, `failure`, `blocked`. IP, логины и идентификаторы профилей в labels не попадают. Если вход снаружи полностью закрыт Authelia/Authentik и внутренний лимит не нужен, его можно отключить через `INPX_LOGIN_RATE_LIMIT_ENABLED=false`; счётчики попыток при этом останутся.

Для OPDS действует отдельный от входа в веб-интерфейс лимит неудачных попыток с одного IP: по умолчанию 8 за 15 минут (`loginRateLimitMaxAttempts` / `loginRateLimitWindowMs`). Ответ на превышение — HTTP 429 с `Retry-After`. Запрос без Authorization только получает стандартный Basic Auth challenge и не расходует лимит. Успешный OPDS-вход не сбрасывает предыдущие ошибки, чтобы известный пароль одного профиля не позволял перебирать другие. Метрики различают попытки с `kind="opds"`. Адреса IPv6 считаются по подсети /64.
