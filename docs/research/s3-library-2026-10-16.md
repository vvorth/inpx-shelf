# Library on S3: design notes and measurements (2026-10-16)

The S3 backend for libraries was built on `feature/s3-library` (commits `S3 plan` … `S3 step 7`). How it
works now is documented in `server/AGENTS.md`, `docs/sources.md` and `docs/docker.md`. This file keeps what
those docs don't: the reasoning, the numbers, and what is still unmeasured.

## Why native, not a mount

The target is AWS Fargate. Fargate has no `/dev/fuse` and no `SYS_ADMIN`, so `rclone mount` and
`mountpoint-s3` can't run there. EFS would need no code, but the library was wanted in S3.

## Design in one paragraph

`LibraryFs` sends `s3://` paths to `S3Fs` (AWS SDK) and every other path to `fs`. 7-Zip (WebAssembly) reads
synchronously inside the archive worker thread. An S3 archive is therefore a custom Emscripten file node:
each read posts a request to a fetcher thread and blocks in `Atomics.wait` until the ranged GET returns.
Blocks are 256 KiB; adjacent missing blocks come in one request; a 32 MiB LRU per archive thread, keyed by
ETag, serves repeat reads. Folder listings are cached until the periodic INPX check, because libraries
are read-only.

## Measurements

The environment was a sandbox VM with SeaweedFS (S3 gateway) in Docker on the same host. **Latency to real
S3 was not measured.**

| What | Result |
|---|---|
| Full Flibusta INPX import (708,358 books), INPX in S3 | 87.8 s |
| Same INPX from local disk | 78.0 s |
| Requests, first book from a 43 MB zip | about 4: 6-byte signature, HEAD, start/tail blocks, the entry's blocks |
| Requests, another book from the same zip | 1 HEAD; the blocks come from the cache |
| Solid 7z (12 MB, one block) | the whole solid block, in one GET thanks to merged block reads |
| `pkg` binary (`node24-linux-x64`) | imports from S3 and serves a book; the fetcher eval-worker and the SDK are bundled |

Expected on real S3: each GET costs about 20–50 ms, so the first book from an archive costs about
100–250 ms on top of today's path, and repeat books from that archive cost one HEAD.

## Open

- Measure cold-book latency and block size (256 KiB vs larger) against real S3 from Fargate.
- Measure how long a `library.sqlite` rebuild on Fargate start takes with `CACHE_DIR` on ephemeral storage.
  The sandbox number (88 s) is CPU-bound and only indicative.
- Buckets from different providers or with different credentials at the same time are not supported:
  there is one SDK client for every bucket.
