# Code audit, 2026-10-22

Branch `dev` at `19b2827`. Scope: the whole repository (server, client, shared, scripts, build, CI, Docker, installer), read as if taking over maintenance for years. Six independent read-throughs by area, then every finding rated critical, high or medium was re-verified by reading the code paths again; two were reproduced in plain Node. Nothing was changed.

The previous audit (`audit-2026-09-14/`) is not repeated: every fix it claims was checked and holds (backups under `dataDir/backups`, per-file write queues, race-safe `secret.key`, scrypt with legacy migration, transactional restore with journal, request limits, OPDS rate limits).

Severity means realistic impact on a typical deployment: a self-hosted catalog with a few profiles, often behind a reverse proxy, sometimes with guest access or Kobo sync on. CONFIRMED means the whole path was traced in code (or reproduced); SUSPECTED means the mechanism is clear but one step was not exercised.

## Summary

| Severity | Count | Headline |
|---|---|---|
| Critical | 1 | The service worker caches API GET responses and replays them to the next user of the browser |
| High | 3 | Prototype pollution through Kobo book UUIDs; another user's reading position imported into a fresh profile; infinite retry loop on a CSRF failure |
| Medium | 15 | Library paths leak to readers; import plants credentials into open profiles; unbounded per-profile data; unbounded remote buffering; cache key explosion; restore applies auth settings live; whole-book parse per view under a root path; startup blocked by remote libraries; IPv6 proxies untrusted; progress conflict rules; stale state across profile switch; supply-chain gaps |
| Low / info | ~45 | Listed per area below |

Fix order recommended: the critical and the four client/Kobo items first (each is under a day), then the medium server items, then the supply-chain hardening, then the refactor roadmap at the end.

## Critical

### C1. Service worker caches every same-origin GET, including the API — CONFIRMED

`client/assets/sw.js:92-100`. After the `navigate`, shell-path and `/book`, `/cover/` branches, every other same-origin GET is answered cache-first and stored on `response.ok`:

```js
event.respondWith(caches.match(request).then((cached) => cached || fetch(request).then((response) => {
  if (response.ok) { ... cache.put(request, copy); }
```

The worker is registered at the app base path (`client/main.js:328-329`) and the API is mounted at `<root>/api` (`server/index.js:211`), inside that scope. Since the shared route table made reads GET requests (`shared/apiRoutes.js:7-42`, commits `e502b7b` and `79c5d0a` of 2026-10-20/21) this branch now stores `api/config` (with the CSRF token, profile list and current profile), `api/me/library`, `api/reading-lists`, `api/admin/dashboard`, `api/kobo-devices`, `api/books/:uid/reader-state` and every other read. The server's `Cache-Control: no-store` does not apply to the Cache API. The worker predates the REST conversion, when every API call was a POST, which is why this has not been noticed.

Consequences: on a shared browser the next person gets the previous profile's library, lists, devices and admin dashboard after a logout (the `DELETE session` call never touches the cache); `api/config` is frozen until a new build id rotates the cache name, so login state stops updating; OPDS feeds under the root are cached too.

Fix: invert to an allowlist. Cache only the hashed bundle assets and `APP_SHELL`; do not call `respondWith` for anything under `api/`, `opds/`, `remote/`, `kosync` or `admin-backups`, or for any request carrying `X-Inpx-Api`. Add a test in `scripts/client-tests.js` that a non-navigate `GET api/config` is neither served from nor written to the cache (the existing test covers navigations only). Ship with a cache-name bump so installed workers drop the old cache.

## High

### H1. Prototype pollution through the Kobo book UUID — CONFIRMED, reproduced

`server/core/kobo/index.js`: `putState` (864-917), `deleteBook` (966-972), `getState` (855-858), `metadataRequest` (846), `download` (1027), `noteFileChanged` (1053), `editTagItems` (1015) and `Covers.js:16` look device-supplied path parameters up as plain-object keys: `device.books[uuid]`, `rows[uuid] = rows[uuid] || this.emptyState(now)`, `target.books[uuid].deletedOnDevice = true`. `books` and `states[userId]` are `{}` literals (`KoboStore.js:39, 883`), so `books['__proto__']` is `Object.prototype`, truthy, and passes `if (!row)`. Reproduced in plain Node with the same assignments: `DELETE /kobo/<token>/v1/library/__proto__` sets `Object.prototype.deletedOnDevice = true`; `PUT .../__proto__/state` with `{ReadingStates:[{StatusInfo:{Status:"Finished"}}]}` sets `Object.prototype.status`, `lastModified`, `priorityTimestamp`.

Process-wide until restart: every `error.status` reads `'Finished'`, so `ProfileAccess.httpGuard` (`ProfileAccess.js:185`) throws on every OPDS/book auth error; every Kobo row reads as deleted on every device; `for...in` over any object yields the polluted keys. Attacker: anyone holding a device token, which is any non-admin profile with Kobo enabled. The request returns 200 and `JSON.stringify` hides the pollution from `kobo-sync.json`. `kosync-tests.js:120` tests `__proto__` for KOReader; no such test exists for Kobo.

Fix: `router.param('uuid')` and `('tagId')` rejecting anything that is not a v5 UUID; filter `tagItemUuids` the same way; a `rowOf(device, uuid)` helper using `Object.hasOwn`; create `books` and `states[userId]` with `Object.create(null)` or Maps in `KoboStore`. Same key pattern in `KoboStore.importUser` (348-355) on restore is admin-only and local, but should use the same filter. Regression test with `__proto__`, `constructor`, `toString` on every per-book route.

### H2. Another user's reading position leaks into a new profile — CONFIRMED

`client/share/readerStorage.js:289-291`: a signed-in user without a per-user bucket falls back to the global `progress` map, which `writeProgress` fills for every user (`:369`). `readerProgressSync.applyOpeningProgress` (`client/components/Reader/readerProgressSync.js:23-30`) hands it to `readerProgress.opening` (`client/share/readerProgress.js:553-571`), which may pick it and set `upload: true`, after which it is PATCHed into the new user's server profile. Shared-browser privacy leak plus silent progress corruption.

Fix: with a `userId`, read only `byUser[userId]`; write the global map only for the guest id; add a case to `scripts/reader-tests.js`.

### H3. `Api.request` loops forever on `bad_csrf_token` — CONFIRMED

`client/components/Api/Api.vue:319-330`: on `bad_csrf_token` the client refreshes the config, resets `retries = 0` and the `while(1)` continues with no cap or delay. `upload()` caps the same case (`:283`); `request()` does not. Trigger: the browser does not keep the session cookie (cookies blocked; `Secure` flag set because a trusted proxy reports https while the user browses http; `Path` mismatch). Every write then hammers the server with a new session per iteration.

Fix: one refresh, then throw, as in `upload()`.

## Medium

### M1. Absolute server library paths are in every book record — CONFIRMED

`server/core/search/CatalogIndex.js:1317-1329` (`bookRows`) adds `sourceLibDir: live.libDir || source.lib_dir || ''` to every record, and nothing strips it on the way out: `catalogSearch`, `get-book`, `get-book-info`, author and series lists, reading lists (`ApiController.js:617-640`, `WebWorker.js:366-388, 1550-1555`). These are `guestActions` (`ProfileAccess.js:8-14`), so with guest access an anonymous visitor learns the host's library directory. `get-book-info` also writes the record into `<bookDir>/<hash>.i.json` (`WebWorker.js:1477, 1522`), which `express.static(config.bookDir)` serves (`static.js:497`); the guard at `static.js:323-336` blocks `.d.json` for exactly this reason but misses `.i.json` (and `.dev` dumps in development). The project's own policy treats the path as private (`errorText` scrubbing, `testServerDetailsStayPrivate`).

Fix: resolve `libDir` by `sourceId` inside `LibraryAssets` (as `getBookLink` already does for remote sources) and strip `sourceLibDir` from every record leaving the worker; extend the static guard to `.i.json`/`.dev` or write the info cache outside `bookDir`; add the assertion to the privacy test.

### M2. Import plants OPDS/KOReader credentials into an open profile — CONFIRMED

`ApiController.importReadingLists` (`ApiController.js:931-946`) strips only `kobo`, `emailTo` and `telegramChatId` for an unprotected profile. `Lists.importData` (`readingLists/Lists.js:379-384`) then accepts `kosyncKeyHash` (any 64-hex) and `opdsPasswordHash` (when the profile has a login). The direct routes `setOpdsPassword` and `createKosyncPassword` (`ApiController.js:1060-1082`) require a protected profile; the import route does not. Anyone who can select a passwordless profile can plant credentials they know, which persist after an admin later sets a password.

Fix: delete `data.user.opdsPasswordHash`, `kosyncKeyHash` and `kosyncProgress` in the same unprotected branch, or pass a `protected` flag into `importData` so one place decides.

### M3. Unbounded per-profile data from any authorized profile — CONFIRMED

`updateReaderProgress` (`ApiController.js:697-704` → `ReaderState.js:143-207`): `bookUid` is only trimmed (`ReadingListStore.js:637-642`), never format-checked or matched against the library (unlike `markReaderBooksRead`, `WebWorker.js:992-998`). `addReaderBookmark` (`ReaderState.js:296-319`): no length cap on title/excerpt/note, no cap on bookmarks per book or profile. `importData` caps one request at 1000 lists / 100k books but totals accumulate across imports; `KoboStore.importUser` states likewise. Every write rewrites the whole `reading-lists.json`; every uncached load parses, normalizes and `structuredClone`s it. In a 2 GB container this is a cheap memory and CPU exhaustion by one reader.

Fix: validate uids as `/^[A-Za-z0-9+/]{43}=$/`; cap bookmark text and bookmarks per book; cap progress rows per profile with eviction by `updatedAt` (as `Discovery.js:57` already does for events); cap lists per profile and books per list; refuse progress for uids the library has never seen unless they already exist in the profile.

### M4. Unbounded buffering of remote-library responses — CONFIRMED

`server/core/RemoteLib.js:107-118` (`getCover`) does `Buffer.from(await response.arrayBuffer())` with no size cap, and checks the content type only after the body is in memory; `listSources` (68-72) buffers `response.json()` unbounded. `saveBody` (50-66) caps INPX and book downloads at `maxPayloadSize` but covers and listings bypass it. Any visitor's cover request triggers the fetch (`LibraryAssets.js:368-370`), so a compromised remote inpx-shelf can push gigabytes into the container.

Fix: stream covers through the same `Transform` limiter with a small cap (5 MB) and reject by `content-length`/type before reading; cap `listSources`.

### M5. Discovery cache key explosion — CONFIRMED

`server/core/discovery/ExternalShelf.js` (`rememberExternalDiscoveryShelf`, around 565): the cache key includes `pageLimit`, `externalBrowseUrl`, `externalTtlMinutes` and the joined `externalLanguages` (up to 10 arbitrary codes). Each new key builds a shelf, stores up to 480 cloned records in memory and in `discovery-cache.json`, and `saveDiscoveryDiskCache` rewrites the whole file per insert. `pruneDiscoveryCache` evicts by TTL and library hash only, never by count. Any signed-in profile supplies these parameters (`ApiController.js:534-554`).

Fix: cache one canonical shelf per `(inpxHash, month, browseUrl)` and filter by language/limit per request in memory; bound the cache (LRU) and never persist per-user variants. Also return stale data while refreshing instead of making the first request after expiry wait for two SPARQL calls.

### M6. Restore applies auth-critical settings at once and keeps no pre-restore copy — CONFIRMED (design)

`AdminBackup.importAdminBackup` (`AdminBackup.js:289-298, 345`): `localKeys` exclude only paths, converters and release links, so a restored `config.json` carries `authMode`, `trustProxy`, `proxyAuthHeader`, `trustedProxyCidrs`, `requireAuth`, `guestAccess`, `proxyBindProfile`, `remoteAccess`, `metricsToken` and `librarySources` with remote tokens; `Object.assign(this.config, runtimePatch)` applies them immediately and `Security.js:286, 362` read them per request. A backup from another host or an upstream inpx-web backup can open header spoofing or lock the admin out. The four user-data files are overwritten with no snapshot; the journal is deleted at commit (`BackupTransaction.js:66`), so restoring the wrong archive is irreversible. Admin-only, hence medium.

Fix: inside the same lock set, create a `pre-restore` snapshot (keep 3) before commit; list the security keys that differ from the running config in the restore result and admin event, or keep them local unless the admin opts in; map the OpenSSL error for a config encrypted with another server's key (`BackupArchive.js:219-221`, `AdminBackup.js:284`) to a clear message.

### M7. Book info cache never validates under a root path; whole-book parse on the main thread — CONFIRMED

`WebWorker.js:1512` stores the cover as a URL (`${bookPathStatic}/${hash}${ext}`, where `bookPathStatic = ${rootPathStatic}/book`); the freshness check at `:1543` builds `coverFile = ${publicFilesDir}${tmpInfo.cover}`, i.e. `<publicFilesDir>/<root>/book/<hash>.jpg`, while the file lives in `<publicFilesDir>/book/` (`index.js:78-79`). With any non-empty `server.root`, `!pathExists(coverFile)` is always true and every book page view of an FB2 with a cover re-reads, re-decodes and fully re-parses the book and rewrites `.i.json` and the cover.

Independently of that bug, `restoreBookInfo` → `Fb2Helper.getDescAndCover` parses the entire FB2 into a nested tree on the main thread (`Fb2Helper.js:284-301`, `WebWorker.js:1291-1376`): a 10-20 MB book blocks the event loop for seconds and allocates hundreds of MB; `pendingBookInfos` dedups only the same book. No test covers `getBookInfo` under a root path.

Fix: compare against `${bookFile}${path.extname(tmpInfo.cover)}` (or store the file name, not the URL). Compute TOC and word counts with `sax.parseSync` callbacks and build a tree only for `<description>`, or run the extraction in a worker.

### M8. Startup blocks on remote library sync — CONFIRMED

`server/index.js:126` awaits `new RemoteLib(config).syncAll()` before `listen`; `RemoteLib.request` uses a 5-minute `AbortSignal.timeout` (`RemoteLib.js:200`). A black-holed remote host delays listening by up to 5 minutes per source; `/health` is down meanwhile and the Docker healthcheck restarts the container. The comment at `:254-255` already accepts a stale INPX; move the sync after `listen` or use a short connect timeout at startup.

### M9. IPv6 reverse proxies can never be trusted — CONFIRMED

`server/core/Security.js:19-40` (`parseIpv4`) returns null for anything but dotted IPv4, `::ffff:`-mapped and literal `::1`; `isTrustedProxyAddress` (293-299) therefore rejects nginx or Traefik on an IPv6 address. In `authMode: proxy` every request then gets `403 Direct access is forbidden`; otherwise forwarded proto/host are ignored, cookies lose `Secure` and Kobo URLs use the internal host. Fails closed, so no bypass. Fix: `net.BlockList` (`addSubnet` for both families, `check(address, family)`), keeping the `::ffff:` normalization.

### M10. Reading progress conflict rules favour whoever writes last — CONFIRMED

Three related gaps. Web reader: `readerProgressSync.js:143-153` re-sends with `force: true` whenever the server's position differs from the one just sent, and `patchReaderProgress` skips the "older than current" check under `force`, so a delayed flush from one browser overwrites a newer position from another device. Server: `ReaderState.js:156-191` trusts the client's `updatedAt` without clamping (Kobo clamps to now+5 min at `kobo/index.js:936-939`), so one device with a future clock makes every later real update be dropped until a force. KOReader: `Kosync.js:117` stamps pushes with server time, so a stale device position always wins; inherent to the protocol but `docs/koreader.md` says "if newer".

Fix: force only when the server-returned `updatedAt` is older than the request's, or after an explicit "keep local" choice; clamp `patchUpdatedAt` to now+5 min; document the KOReader semantics.

### M11. Kept-alive pages show the previous profile's per-user state — CONFIRMED

`SearchPage.vue:300-305` reloads on activation only if the query key changed; `states` (read marks, progress, in-list flags) persist and are rendered via `BookCollection`. Same in `BookPage.vue:351-356`, `AuthorPage.vue:224-228`, `SeriesPage.vue:128-132`. `ListsPage` and `DiscoveryPage` handle it. Fix: include `config.currentUserId` in each page's load key or clear `states` on user change. Related: `Api.updateConfig` is called unawaited at mount and after the busy dialog (`Api.vue:87, 270`); a slow early `get-config` landing after login can overwrite the authorized config with an anonymous one (SUSPECTED). A sequence counter dropping out-of-order responses fixes it.

### M12. Corrupt user-data files silently reset to defaults — CONFIRMED

`ReadingListStore.js:426-436`: on a parse failure the file is copied to `.broken-*`, defaults are written and the server continues with no profiles; nothing is logged at error level and no admin event is raised. `KoboStore.readData` (`KoboStore.js:133-141`) behaves the same. The next successful write then persists the empty state. Fix: log at error level and raise an admin event naming the broken copy; preferably refuse writes until an admin acts. Related: `normalizeMetadataOverrides` throws on one bad row (`ReadingListStore.js:153-154, 170-185`) and runs on every load, so one hand-edited entry fails every request; `normalizeEntries`/`importData` throw `TypeError` (→ 500) on `null` elements.

### M13. Supply chain and release integrity — CONFIRMED

- Every GitHub Action is pinned by major tag (`check.yml:26,29,47`, `ci.yml:50`, `docker.yml`, `release.yml`), including `softprops/action-gh-release@v3` in a job with `contents: write`. No `.github/dependabot.yml`. Pin to commit SHAs with a version comment; add Dependabot for `github-actions` and grouped monthly `npm`.
- Releases publish only `*.zip`/`*.exe` (`release.yml:299-307`): no `SHA256SUMS.txt`, no provenance attestation, unsigned Windows binaries.
- `"postinstall": "npm run build:client-dev"` (`package.json:32`) compiles the client on every plain `npm install`/`npm ci` and makes `npm install --omit=dev` fail (webpack is a dev dependency). CI and Docker are protected by `--ignore-scripts`. `nodemon` is used by the `dev` script but declared nowhere, so `npm ci && npm run dev` from `docs/development.md` fails on a clean checkout.
- `npm audit` is a hard gate on every push (`check.yml:36`): it blocked four consecutive dev runs on 2026-10-21/22 for a transitive `follow-redirects` advisory unrelated to any commit. Keep it blocking for release, make it `continue-on-error` on PRs plus a scheduled daily job, and let Dependabot deliver the fix.
- Toolchain: eslint 8.57 (EOL since October 2024, legacy `.eslintrc` with `valid-jsdoc`), eslint-plugin-vue 9 (open moderate advisory), webpack-dev-middleware 6.1.2 (open high advisory, dev mode only). Dev-only audit: 8 findings, 2 high.
- `engines.node >= 24` is not enforced (`node:sqlite` throws at require on older Node); add `engine-strict=true` to `.npmrc` or a startup check with a clear message.

### M14. Docker and Windows packaging — CONFIRMED

- `docker-entrypoint.sh:15-24` `exec "$@"` for any non-dash first argument runs before the PUID/PGID drop (51-66), so an explicit command runs as root. `scripts/binary-smoke-test.js:84-89` runs the image exactly that way, so the privilege drop, `chown` and `VOLUME` path are never exercised in CI. Move the drop above the exec branch and add one smoke run with default arguments and `PUID=1000`.
- The binary smoke fixture has no book archive (`binary-smoke-test.js:11-31`) and the checks hit only `/ready`, `/health`, `/`, `/opds` 401 and three API calls: 7z-wasm, `ZipReader`, cover tools and `/book/by-uid` are untested inside the packaged binary. Add a tiny zip+fb2 and fetch a book and a cover.
- Windows installer (`build/windows-installer.iss:72-79`) passes `--data-dir={localappdata}\inpx-shelf` to shortcuts, while a direct launch of `inpx-shelf.exe` uses `<execDir>\.inpx-shelf` (`config/index.js:175-177`; the LOCALAPPDATA fallback at 221-247 fires only when `execDir` is unwritable, and `Programs` is writable): two independent sets of profiles, lists and `secret.key`. Default to `%LOCALAPPDATA%\inpx-shelf` for `process.pkg && win32`, keeping a legacy dir if present.
- `createWebApp.js:74-90` removes `public/` and re-extracts with no lock or atomic rename; `index.js:87` empties `tempDir` on start. Two instances on one data or cache dir, or a crash mid-extract, leave a half-served app. Extract to `public.<hash>` and rename.

### M15. Metrics token and OPDS burst handling — CONFIRMED

- `/metrics` and `/api/index-status` (`HealthRoutes.js:123-134, 178-193`) check `metricsToken` with a timing-safe compare but no rate limit; a weak admin-chosen token is guessable at line rate. Add `checkLoginRate(req, 'metrics')`.
- `ProfilePassword.derive` throws `passwordCheckBusy` at 4 concurrent scrypt runs (`ProfilePassword.js:32-33`); `ProfileAccess.basicIdentity` (`:133`) does not catch it, so an OPDS client opening 5+ parallel requests before the 10-minute verified cache warms gets HTTP 500 via `httpGuard` → `next(error)`, and the web login form counts it as a failed attempt. Dedupe in-flight verifications per credential and answer 503 with `Retry-After`.

## Low and informational, by area

### HTTP surface and auth
- Session cookie gets `Secure` only when a trusted proxy reports https (`Security.js:116-126, 227-229`); the default `trustProxy: false` deployment behind a TLS-terminating proxy issues a non-Secure cookie and no HSTS. Add a `cookieSecure` option or honour `X-Forwarded-Proto: https` to add (never remove) the flag; document that `trustProxy` is required for `Secure`.
- One upload slot for the whole server (`ApiController.runUpload`, 352-371): a reader's slow 16 MB list import makes the admin's backup restore answer 503. Per-action or per-user slots.
- `get-discovery-shelves?forceRefresh=true` is the only GET that changes server state (admin-only, header-guarded). Make it a POST command to keep the "GET never mutates" rule literal.
- `TELEGRAM_BOT_TOKEN` and `SMTP_PASS` from the environment are written (encrypted) into `config.json` on first start and survive removing the variable, unlike the INPX_* access settings that deliberately avoid this (`config/base.js:403-404`, `config/index.js:70-79`).
- `dataDir` from `config.json` overrides `--data-dir` (`config/index.js:246, 303`), while host, port and admin settings follow CLI > env > file. Make CLI win consistently or document it.
- `requireAuth: true` with `authMode: 'local'` is a no-op (`Security.js:362-386`); the flag effectively means "enforce proxy auth". Rename or document.
- `/book/:fileName/:fileType` with an unknown type returns 500 (`static.js:453-454, 480-491`); cover errors are swallowed as silent 404s (`static.js:118-125, 316-318`); `res.sendFile` after `pathExists` with no callback can 500 if the cache cleaner removes the file in between (SUSPECTED).
- Admin remote-library URL is an admin-controlled SSRF surface (`AdminService.js:509-516`); optionally refuse loopback and private ranges unless allowed.
- Dead parameters: `assertProfile(identity, req.userId)` can never fire for the API; `query: 'json'` on author/series book lists is ignored; `authorId` accepted and ignored.
- Message-based error typing: `ApiController.errorStatus` (227-235) maps HTTP status by `e.message` strings while other paths use `e.status`, `e.code`, `denied()` and `httpError()`; a renamed constant silently changes a status code.
- `dispatch` (`ApiController.js:375-382`) reflects action names onto any controller method; use an explicit handler map.
- Express 5 blockers: `req.query.user = ...` (`ProfileAccess.js:172`) and `req.query[key] = ...` (`opds/index.js:48`) rely on a mutable cached `req.query`; wildcard routes `${opdsRoot}/*` and `router.all('*')` need the `/*splat` syntax.
- Tested well: CSRF on every write route, `X-Inpx-Api` + Origin + `Sec-Fetch-Site`, cookie signing and lifetimes, fixation, revocation, unknown-login timing, OPDS rate limit and scope, guest route matrix, `/book` traversal, XFF spoofing, remote API 401/429/ETag. Not tested: `/metrics` auth paths, `admin-backups/:fileName` traversal, cookie `Secure` behind trusted vs untrusted proxy, IPv6 proxy, 413 without `Content-Length`, absence of `sourceLibDir` in responses.

### Library, archives, converters
- INPX `folder`/`file` are used as paths without containment (`LibraryAssets.js:61-80`): a hostile INPX with `../` reads outside the library. Trusted input today; cheap to reject at import and to add a `path.relative` check.
- cp866 fallback replaces undecodable characters with `?` and runs 7-Zip without `-spd` (`ZipReader.js:46-54`, `SevenZipEngine.js:577`): a Cyrillic name becomes a wildcard matching every same-length entry, extracting a whole archive into WASM memory. Resolve the name against the listing and extract one entry.
- User regexes in `~` mode run over whole name tables as a JS SQL function (`CatalogIndexQueries.js:36, 60-63`); `checkSearchRegExp` blocks backtracking but `~.*` still scans ~1M rows synchronously in the library thread, reachable via OPDS search. Require a literal prefix.
- `updateBook` sends a caller-supplied `id` to a DB opened by path (`CatalogSearch.js:404-417`, `CatalogIndex.js:1225-1226`); between `fs.move` and `openIndex` in `rebuild` an admin edit can hit the wrong book in the new DB. Resolve `id` from `_uid` inside the thread.
- No `unhandledRejection` handler in `AsyncExit` (`AsyncExit.js:38-43`): Node exits without `closeDb` or log flush.
- `S3File` LRU caches `subarray` slices of one fetch, so one surviving block pins a multi-MB buffer; resident memory can exceed `maxCacheBytes` (`archive/S3File.js:334-350`). Copy per block.
- `scheduleCacheClean` returns when the interval is 0 even with a cron schedule set (`CacheCleaner.js:106-108`).
- `LockQueue.js` is dead and its `wait()` breaks the lock; `WorkerState.js` is a relic whose `cleanStates` drops `server_state` after 59 idle minutes so `getIndexStatus` silently returns `{}`.
- `InpxParser.js:143-146` assigns raw `structure` field names, so a field named `_uid`, `folder` or `sourceId` overwrites internal fields; `.inp` detection is case-sensitive.
- 7-Zip extract-to-memory has no cap (recoverable: worker restart); `VACUUM` with `temp_store = FILE` needs a full DB copy in the SQLite temp dir, often tmpfs in containers (document `SQLITE_TMPDIR`); S3 listings are cached until `periodicCheckInpx`, invisible with `inpxCheckInterval` 0.
- Verified correct: parameterized SQL everywhere, normalized FTS tokens, `ensure()` merging, same-call book records, reader-thread restart, zip-slip protection in `extractToFile` and `EpubRestorer`, `spawn` without shell with fixed arguments, gzip/JPEG/PNG caps, atomic cache publishing, conversion queue and process-group kill.

### User data and backups
- Backup zip contains `secret.key` plus the config: plaintext-equivalent secrets, admin-download only. Document, or offer an optional passphrase.
- The generated admin password is logged at WARN (`ReadingListStore.js:93`) and WARN lines are mirrored into the admin event log (`WebWorker.js:88-91`).
- Every write invalidates the parse cache (`writeDataNow` refreshes `persisted` but not `loaded`, 563-567); a coarse mtime plus equal size could in theory return a stale snapshot (SUSPECTED). Set `loaded = persisted` after writes.
- `writeFileAtomic` has no retry on `EPERM`/`EBUSY` for Windows rename when an indexer holds the target.
- `normalizeUser` starts from `Object.assign({}, fallback, item)` so unknown fields in a restored file pass through unvalidated; `KoboStore.normalizeData` keeps `states` and `tags` as-is; ISO strings are trimmed but not validated, so a non-ISO `updatedAt` defeats the "older import does not roll back" guard.
- `state.sqlite` is not fully rebuildable: `kosync_document` is learned only when a file is served.
- Implicit locking by `method.constructor.name === 'AsyncFunction'` (`ReadingListStore.js:659-666`): a non-async method returning a promise runs unlocked silently. `KoboStore.mutate(task)` is the cleaner model.
- A corrupt restore journal makes the server refuse to start with a message that does not name `.restore-transaction`.

### Kobo, OPDS, discovery, delivery
- `StoreProxy.js:17-22, 39-46` forwards all request headers except a short skip list (hop-by-hop headers and `x-kobo-synctoken` go to kobo.com) and relays all response headers back; a store `x-kobo-synctoken` would be decoded as a sync token and force a full resync (SUSPECTED). Allow-lists both ways. The host is fixed; not an open proxy.
- `docs/users-opds.md` says admins see password profiles in OPDS; `assertProfile` forbids it for every identity, so the `viewer.admin` branch in `opds/Auth.js:17-20` is unreachable. Fix the doc or the code.
- A `PUT state` landing during a long sync is overwritten by the sync's snapshot (`kobo/index.js:815-818`; the comment claims the opposite).
- Two records with one `libid` in one source collapse into one Kobo book (`collectWanted` 224-231); `rekeyOrphans` knows the case, `collectWanted` does not.
- OPDS: title search is capped at 360 results silently; `TitlePage` asks for 1000 with no pagination; author page loads the whole list and filters in JS.
- Telegram caption inserts `${TITLE}` raw (a >1024-char caption yields a bare Bot API 400); a user may point `telegramChatId` at any chat the shared bot is in.
- Verified correct: Kobo token entropy, hashing, masking and revocation; body parsed after auth with limits; KOReader document hashes validated with `Object.hasOwn`; OPDS XML built from objects with central escaping and a hostile-text test; Wikidata SPARQL strings static; `RemoteLib` TLS verified, `redirect: 'error'`, timing-safe token compare.

## Code quality and refactor roadmap

The codebase is in better shape than its age suggests: parameterized SQL, atomic writes, encrypted secrets, a single route table shared by client and server, real tests with temp dirs and real SQLite, 7-Zip and S3 mocks. The structural debts are these.

1. **Prototype mixins** (`Object.assign(WebWorker.prototype, require(...))` across 8 files; same on `ReadingListStore`, `KoboService`): one implicit `this` with lazily created state (`if (!this.pendingBookRestores)` and friends) that `resetLibraryAssetCaches` must enumerate by hand; no jump-to-definition; tests build workers with `Object.create(WebWorker.prototype)`. Move toward collaborating classes (`BookFiles`, `LibraryAssets` owning its caches, `ReadingLibrary`) with `WebWorker` as a thin facade. Do it file by file; each move is mechanical.
2. **One error type** with `status` and an i18n key, replacing the `e.message` table in `ApiController.errorStatus`, the `"404 "` prefix sniffing in Kobo, and the four copies of 429 handling. Fixes the 500s in M15 as a side effect.
3. **Boundary helpers**: `publicBook(record)` stripping internal fields (M1); a `fetchLimited(url, {maxBytes, timeout})` used by `RemoteLib`, Wikidata, Telegram and the release check, retiring `FileDownloader` and axios on the server (M4); `config.rootPath()` and shared path helpers replacing six copies of root-path normalization; `net.BlockList` for proxy trust (M9).
4. **Input schema and caps**: one small validator (uid format, text lengths, ISO dates, per-profile row limits, unknown-field allowlist) applied in `normalize*` and on load. Replaces ~40 ad hoc checks and delivers M3, M12 and the low-severity normalization items.
5. **User data store**: `reading-lists.json` is one file for all users, rewritten whole per mutation, held 2-3 times in memory, serialized by one lock. The 700k catalog is fine; N readers times progress, bookmarks and the 5000-event discovery cap per user is what grows. `node:sqlite` is already in `StateStore`; a `user-data.sqlite` with one-time import of the JSON, and backup export/import keeping the exact four-file shape, removes the whole-file lock and the clone per request. Largest item; plan it, do not rush it.
6. **Dependency diet** (Node 24 builtins): `minimist` → `util.parseArgs`; `lodash` (only `cloneDeep`, `pick`, `omit`, `isPlainObject`) → `structuredClone` plus three one-liners; `axios` + `form-data` → `fetch`/`FormData`; `node-stream-zip` → the existing `ZipReader` (only `BackupArchive.js` uses it); `iconv-lite` decode → `TextDecoder` (keep only cp866 encode); `fs-extra` 10 → at least 11, full removal is mechanical but large. `@aws-sdk/client-s3` plus `@smithy` (~22 MB) ride in every binary because pkg traces statically; accept or make an S3-less build flavour. Client-only libraries sit in `dependencies`.
7. **Toolchain**: eslint 9/10 flat config, eslint-plugin-vue 10, webpack-dev-middleware 7; drop babel-loader (the `.babelrc` targets `esmodules`, so it transforms nothing) once `@babel/eslint-parser` is replaced by espree. About a day.
8. **Client**: keep `vueComponent.js` for legacy components and write new or leaf components in `<script setup>`; the 14-layer reader prototype (~5k lines over ~170 reactive fields) is the one place where a composable extraction would pay, but without a browser test harness it is 3-5 weeks of regression risk; defer until Playwright covers the reader. vuex → Pinia is about a day (one `settings` object). Move `Fb2Parser`, `XmlParser`, `ReaderContent` and `LockQueue` out of `server/` into `shared/` so a Node-only import can never break the client build. Reduce the 69 `!important` and unscoped Quasar overrides in `App.vue`.
9. **Express 5**: stop mutating `req.query`, fix wildcard routes, then drop the manual async wrappers. Do it when something else forces the upgrade.
10. **Tests**: `node --test` per file; split `release-smoke-tests.js`; direct tests for `BookDelivery`, `CacheCleaner`/`CacheSchedule`, `ExternalShelf`/`WikidataTable`, `kobo/Preparation`; a packaged-binary smoke that opens a real archive and cover; a Docker smoke on the default entrypoint with `PUID`; a browser smoke for the service worker and keep-alive pages.

## Things done well

Session cookie HMAC with timing-safe compare, fixation reset, absolute and idle expiry, revocation on credential change; CSRF token plus custom header plus Origin and `Sec-Fetch-Site` checks on every write route, verified for every route by a test; forwarded headers honoured only from trusted CIDRs, rate limits keyed on the resolved client IP with IPv6 bucketing; scrypt with dummy derivation for unknown logins and a verification cache; bodies authorized before they are read, with explicit limits per kind; secrets masked in logs by key pattern and in Kobo paths; `secret.key` created race-free with 0600; atomic writes with fsync and rename through per-file queues; transactional restore with journal and startup recovery; whitelist-only backup entries with declared and streamed size checks; Kobo tokens hashed and masked; OPDS XML built from objects with central escaping; `safeHtml` minimal and tested; FB2 to HTML output escaped with `data:`-only images; parameterized SQL with constant identifiers; zip-slip protection on every extraction path; conversion queue with timeouts and process-group kill; one reusable CI workflow for PRs, dev and releases on both platforms with least-privilege permissions, atomic release pushes and digest-joined multi-arch images; fully isolated, fast test suite.

## Environment note

This review ran on a box with Node 22, not the required 24. ESLint and the i18n check pass; `npm run test:release` fails 10 of 263 tests here, all with `NOT NULL constraint failed: column_data.data` from `CatalogIndex.finishBuild` (`CatalogIndex.js:475`). Cause: Node 22's `node:sqlite` binds a `Buffer` that views a zero-length `ArrayBuffer` as NULL (`Buffer.from(new Uint8Array(0).buffer, 0, 0)`; `Buffer.alloc(0)` binds fine), which happens when a filter column such as `genreList` is empty in a tiny test library. Node 24 binds it as an empty blob, and CI is green on the same commit. Low: if Node 22 support ever matters, bind `Buffer.alloc(0)` when `byteLength` is 0. The packaged build was not run here. The two reproductions (H1 and C1's cache behaviour) were done in plain Node and in the same `vm` sandbox `scripts/client-tests.js` uses.
